## 1. 목표와 수행 방향

서울 리전의 AWS에 독립된 네트워크를 만들고, EC2 한 대에서 웹 서비스를 실행해 외부 접속을 확인한다. 이후 통신 장애를 근거에 따라 분석하고, 사용한 리소스를 정리하는 전 과정을 제출 자료로 남긴다.

서비스는 **Nginx 기반의 간단한 과제 소개 페이지와 `/health` 엔드포인트**로 구성한다. 과제의 중심인 VPC·라우팅·보안 그룹·IAM을 직접 이해할 수 있도록 AWS 콘솔에서 단계별로 구성하고, 서버 설치와 검증에는 SSH 및 명령어를 사용한다.

필수 요구사항을 먼저 완성한다. HTTPS와 Docker는 선택 과제로 남기고, 기본 제출 범위에는 포함하지 않는다.

## 2. 구현 범위와 설계

| 항목 | 계획 | 선택 이유 |
| --- | --- | --- |
| 리전 | 서울 `ap-northeast-2` | 과제 제약 준수 |
| VPC | 전용 VPC 1개, `10.0.0.0/16` | 기존 환경과 실습 리소스 분리 |
| Subnet | Public Subnet 1개, `10.0.1.0/24` | 단일 서버에 필요한 최소 구성 |
| Internet Gateway | 1개 생성 후 VPC 연결 | 인터넷 통신 경로 구성 |
| Route Table | Subnet에 명시적으로 연결, `0.0.0.0/0 → IGW` | 외부로 향하는 기본 경로 설정 |
| EC2 | 계정에서 프리 티어 적용을 확인한 micro급 1대 | 과제의 비용·규모 조건 충족 |
| OS | Ubuntu LTS | Nginx 설치와 서비스 관리에 사용 |
| EBS | 8GiB로 시작, 루트 볼륨 종료 시 삭제 설정 확인 | 불필요한 저장 공간 방지 |
| 주소 | 자동 할당 퍼블릭 IPv4 | 외부 접속에 사용, Elastic IP는 별도 할당하지 않음 |
| 키페어 | 실습용 1개 | 지정한 개인 IP에서 SSH 접속 |
| 웹 서버 | Nginx, TCP 80 | 정적 페이지와 상태 확인 제공 |
| 검증 방식 | **B: `GET http://<퍼블릭IP>/health`** | 상태 코드와 고정 응답을 함께 증명 |

인스턴스 유형과 Ubuntu 이미지 버전은 생성 직전에 서울 리전의 제공 여부, 호환성, 해당 계정의 프리 티어 조건을 확인해 확정한다. 프리 티어가 적용되지 않으면 생성을 진행하지 않고 과제의 비용 조건을 먼저 해결한다. 퍼블릭 IPv4와 EBS도 비용 확인 대상에 포함한다.

### 네트워크 흐름

```text
외부 사용자 ── HTTP 80 ──┐
                         ▼
인터넷 ↔ Internet Gateway ↔ VPC / Public Subnet
                                  │
                                  └─ EC2의 네트워크 인터페이스에 적용된 SG
                                       └─ EC2 (퍼블릭 IPv4)
                                            └─ Nginx :80

학습자 개인 IP ── SSH 22 ── 같은 인터넷 경로 ── EC2

Public Subnet의 Route Table
  10.0.0.0/16 → local
  0.0.0.0/0  → Internet Gateway
```

서브넷 이름만 Public으로 지정하는 것으로는 부족하다. IGW 연결, 해당 서브넷의 라우팅, EC2의 퍼블릭 IP, 보안 그룹, 서버 실행 상태를 함께 확인한다. 최종 다이어그램은 실제 리소스 구성을 반영해 `docs/architecture.png`로 제작한다.

### 접근 제어

| 구분 | 규칙 및 운영 방식 |
| --- | --- |
| SG 인바운드 HTTP | TCP 80, `0.0.0.0/0` 허용 |
| SG 인바운드 SSH | TCP 22, 학습자의 현재 공인 IPv4 `/32`만 허용 |
| SG 기타 인바운드 | 추가하지 않음. 전체 포트 공개 금지 |
| SG 아웃바운드 | 초기 실습에서는 기본 허용 규칙을 유지해 패키지 설치와 외부 통신 검증 수행 |
| 키 파일 | 저장소 밖에 보관하고 파일 권한을 제한. Git에 포함하지 않음 |
| IP 변경 | SSH 접속 전 현재 공인 IP 확인 후 지정 소스만 갱신 |

Security Group은 서버의 네트워크 통신을 제어한다. IAM은 AWS 리소스를 조회·생성·변경·삭제하는 권한을 제어한다. HTTP 요청을 허용하기 위해 IAM 권한을 확대하지 않는다.

### IAM 계획

실습 전용 IAM 사용자 또는 Role 한 개를 사용한다. 루트 계정으로 실습하지 않으며 `AdministratorAccess`를 부여하지 않는다. 계정에 필요한 주체가 없다면 기존의 권한 있는 계정 담당자를 통해 준비한다.

- EC2·VPC·Subnet·Route Table·IGW·SG·키페어·EBS에 대해 실제 사용할 조회, 생성, 태그, 연결, 수정, 종료·삭제 작업을 정리한다.
- `RunInstances`의 AMI·볼륨·네트워크 관련 권한 등 함께 필요한 권한도 검토한다.
- 지원되는 작업은 서울 리전, 실습 리소스 ARN, `Project=B3-1` 태그 조건 등으로 범위를 제한한다. 조회 등 리소스 단위 제한이 불가능한 작업은 별도 구문으로 분리한다.
- 생성 시 태그 지원 여부와 작업별 조건 지원 여부를 확인해 정책을 작성한다. 태그 조건 하나를 모든 작업에 일괄 적용하지 않는다.
- S3·RDS 등 무관한 서비스와 IAM 권한 변경 권한은 부여하지 않는다. 서버 애플리케이션이 AWS API를 호출하지 않으므로 인스턴스 Role은 기본 구성에 추가하지 않는다.
- 권한 오류가 발생하면 거부된 작업과 리소스를 확인하고 필요한 권한만 보완한다. 최종 정책을 `infra/iam-policy.json`에 기록한다.
- Billing 확인은 별도 조회 권한이 있는 주체가 수행할 수 있다. 이를 위해 실습 주체에 관리자 권한을 추가하지 않는다.

## 3. 웹 서비스 구성

| 경로 | 응답 | 용도 |
| --- | --- | --- |
| `/` | HTTP 200, 과제명과 `Hello Cloud`를 표시하는 HTML | 브라우저에서 서비스 식별 |
| `/health` | HTTP 200, `text/plain`의 `OK` | 필수 외부 접속 증빙 |

페이지에는 과제명, 서비스 소개, 구축 요소를 간결하게 표시한다. 로그인, 데이터베이스, 별도 백엔드 애플리케이션은 구현 범위에 넣지 않는다.

`web/index.html`과 `infra/nginx.conf`를 저장소에서 관리하고 SSH로 서버에 배치한다. Nginx 설정 검사 후 실행 및 부팅 시 자동 시작을 설정한다. 배포 명령은 재현 가능한 형태로 README에 남긴다.

## 4. 단계별 수행 계획

| 단계 | 수행 작업 | 완료 조건 및 증빙 |
| --- | --- | --- |
| 1. 사전 확인 | IAM 주체, 서울 리전, 프리 티어·크레딧·비용 조건, 개인 공인 IP 확인 | 사용할 환경과 권한 범위 확정 |
| 2. 추적 준비 | 실습 리소스 이름·태그 규칙 지정, 리소스 기록표 생성 | 생성한 항목을 정리 목록에서 추적 가능 |
| 3. 네트워크 구성 | VPC, Subnet, IGW, Route Table 생성·연결 | 기본 경로와 Subnet 연결 화면 확보 |
| 4. 서버 생성 | SG, 키페어, EC2 생성, 퍼블릭 IP·루트 EBS 설정 확인 | 지정 개인 IP에서 SSH 성공 |
| 5. 서버 배포 | Nginx 설치, HTML 및 `/health` 설정 적용, 서비스 시작 | 설정 검사 성공 및 localhost 200 |
| 6. 통신 검증 | EC2의 외부 통신 및 학습자 PC의 `/health` 호출 | 아웃바운드 성공, 외부 200·OK 증빙 |
| 7. 장애 분석 | 실제 장애 또는 제한된 HTTP 차단 재현 후 원인 확인·복구 | 보고서 1건 이상 완성 |
| 8. 제출 자료 작성 | 아키텍처 PNG, README, 캡처 정리 | 필수 결과물을 제출 기준과 대조 |
| 9. 리소스 정리 | 의존성을 고려해 종료·삭제하고 잔존 항목 확인 | 정리 근거와 완료 시각 기록 |

예상 작업량은 계정 준비와 권한 조정 시간을 제외하고 반나절 정도로 잡는다. 단계마다 증빙을 확보해 리소스 삭제 후 자료를 다시 수집해야 하는 상황을 방지한다.

## 5. 검증 계획

다음 명령은 구현 시 사용할 예시이며, 현재 검증 결과를 의미하지 않는다.

```bash
# EC2 내부: 인터넷 아웃바운드 확인
curl -I --max-time 10 https://example.com

# EC2 내부: 설정과 실행 상태 확인
sudo nginx -t
systemctl is-active nginx
systemctl is-enabled nginx

# EC2 내부: 웹 서버와 상태 확인
curl -i --max-time 10 http://localhost/
curl -i --max-time 10 http://localhost/health

# 학습자 PC: 실제 퍼블릭 IP로 치환 후 외부 접속 확인
curl -i --max-time 10 http://<퍼블릭IP>/health
```

외부 접속 증빙은 EC2 내부가 아닌 학습자 PC에서 수집한다. 화면에 요청 URL, `200 OK`, 응답 본문 `OK`가 함께 보이도록 캡처하고, 검증 일시와 실행 위치를 README에 기록한다. 인프라 설정 화면으로 SG의 HTTP 공개와 SSH 소스 제한도 확인한다.

README에는 검증 방식 B와 실제 URL을 명시한다. 정리 후에는 서비스 종료 사실과 종료 일시를 표시해 검증 당시의 성공 기록과 현재 접속 상태를 구분한다.

## 6. 트러블슈팅 계획

실제 문제가 발생하면 해당 사례를 우선 기록한다. 문제가 없다면 본인 실습 서버에서 **HTTP 80 인바운드 규칙을 잠시 제거하는 통제된 장애**를 재현한다. SSH 소스 제한은 유지한다.

1. 정상 상태의 localhost 및 외부 `/health` 응답을 먼저 저장한다.
2. HTTP 규칙 제거 후 학습자 PC에서 새 요청을 보내 타임아웃을 확인한다.
3. SSH로 Nginx 실행 상태, localhost 응답, 리스닝 포트, 접근·오류 로그를 확인한다.
4. SG 규칙과 라우팅을 점검해 서버 장애와 네트워크 접근 차단 가설을 구분한다.
5. HTTP 80의 `0.0.0.0/0` 허용 규칙을 복구한다.
6. 외부에서 다시 200과 `OK`를 확인하고, 변경 전후 결과를 기록한다.

보고서는 **증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지** 순서로 작성한다. 명령 출력, 타임아웃, SG 변경 화면과 Nginx 로그를 근거로 사용한다. 접근 로그에 요청이 없다는 사실만으로 원인을 단정하지 않고 내부 정상 응답과 설정 변경 결과를 함께 비교한다. 계획된 장애라면 재현 실험임을 명시한다.

## 7. 리소스 정리 계획

생성 시부터 `docs/resource-inventory.md`에 리소스 종류, ID, 리전, 용도, 생성 시각, 정리 상태, 확인 근거를 기록한다. 태그를 지원하는 리소스에는 `Project=B3-1`을 부여한다.

정리 전에 외부 접속 캡처와 최종 구성 정보를 모두 저장하고 다음 순서로 진행한다.

1. EC2를 **중지(Stop)가 아닌 종료(Terminate)** 하고 종료 상태를 확인한다.
2. EC2에 연결됐던 EBS의 삭제 여부를 확인하고 실습용 잔존 볼륨과 생성한 스냅샷을 삭제한다.
3. Elastic IP는 기본 계획상 미생성이지만 할당 목록을 확인한다. 실습 중 할당했다면 연결 해제 후 Release한다.
4. 남은 네트워크 인터페이스 등 의존 리소스를 확인한 뒤 실습용 SG와 Subnet, 사용자 생성 Route Table을 삭제한다.
5. Internet Gateway를 VPC에서 분리하고 삭제한 뒤 VPC를 삭제한다. 기본 구성 요소는 VPC 삭제 결과에서 잔존 여부를 확인한다.
6. 실습용 키페어를 삭제하고 더 이상 쓰지 않는 로컬 개인 키를 정리한다. 임시 IAM 정책·주체는 기존 공용 자원 여부를 확인해 계정 담당자가 정리한다.
7. NAT Gateway, ELB/ALB, RDS 등 계획에 없는 항목도 실습 중 생성 여부를 확인한다. 미생성은 `해당 없음: 미생성 확인`, 생성한 항목은 삭제 근거를 기록한다.
8. 리소스 목록과 가능한 경우 Billing 화면을 확인한다. 비용 표시 지연을 고려해 조회 시각을 기록하고, 리소스 삭제 여부와 청구 내역을 각각 확인한다.

체크리스트에는 단순 체크 외에 리소스 ID, 완료 시각, 상태 또는 화면 근거를 남긴다. 기존의 다른 프로젝트 리소스는 정리 대상에서 제외한다.

- [ ] 서울 리전 EC2 한 대에 SSH로 접속했고 Nginx가 실행 중이다.
- [ ] localhost가 200을 반환하며, 외부 `/health` 요청이 200과 `OK`를 반환한다.
- [ ] HTTP 80만 전체 공개하고 SSH 22는 지정 IP로 제한했다.
- [ ] 실습 IAM 주체에 관리자 권한과 무관한 서비스 권한이 없음을 확인했다.
- [ ] 실제 구성과 요청 흐름을 나타내는 아키텍처 PNG를 만들었다.
- [ ] README에 방식 B, 실제 접속 URL, 외부 접속 스크린샷을 포함했다.
- [ ] 근거와 재발 방지를 포함한 트러블슈팅 사례를 한 건 이상 작성했다.
- [ ] EC2·EBS·Elastic IP·IGW·VPC 등의 삭제 또는 미생성 근거를 체크리스트에 남겼다.
- [ ] 제출 문서에서 예정 작업과 실제 완료 결과를 구분했다.

최종 완료 시점은 외부 접속에 성공한 순간이 아니라, **접속 증빙과 보고서를 확보하고 실습 리소스 정리까지 확인한 시점**으로 잡는다.
